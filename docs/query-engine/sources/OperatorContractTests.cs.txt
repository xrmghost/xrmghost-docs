        /// <para>
        /// <b>This number is the contract.</b>  It is checked by walking
        /// <see cref="ConditionOperator"/> by reflection, deriving each member's canonical identity
        /// with the production frontend's own rule, and asking a bootstrapped registry whether it
        /// answers — never by counting registry keys (aliases and duplicates would inflate it),
        /// never by counting evaluator classes (one class serves several operators), and never by
        /// trusting a list of names written by hand.
        /// </para>

        /// <summary>
        /// The operators expected to be covered, by name.
        ///
        /// <para>
        /// <b>This list is a diagnostic, not the measurement.</b>  Nothing derives coverage from
        /// it: <see cref="RegisterAll_CoversExactlyEightyEightOfTheSdksEightyNineOperators"/>
        /// asserts the count produced by reflection, and reads this list only to say <i>which</i>
        /// members are missing or unexpected when that count is wrong.  A failure that printed
        /// nothing but "expected 88, got 87" would leave the reader to find the one by hand.
        /// </para>
        ///
        /// <para>
        /// The 1 it omits is <c>childof</c> — see the paragraph below.  The
        /// fifteen fiscal-calendar operators left that list in ADO-2316, the
        /// seven contextual identity ones — the two user-id, the two business-id,
        /// <c>equaluserlanguage</c> and the two team ones — in ADO-2326, in ADO-2337 the five
        /// structural hierarchy ones (<c>above</c>, <c>aboveorequal</c>, <c>under</c>,
        /// <c>underorequal</c>, <c>notunder</c>) together with the two hybrid identity ones, in
        /// ADO-2346 two of the three bitwise ones, and in ADO-2500 the third.
        /// </para>
        ///
        /// <para>
        /// <b>Why the three bitwise operators are here now.</b>  They stood out of this list on
        /// the belief that answering them would mean modelling Dataverse's access masks, and that
        /// belief named the wrong thing.  Each is one bitwise clause over the integer value a row
        /// holds for <i>any</i> integer attribute of <i>any</i> table — <c>mask</c> is
        /// <c>(value &amp; operand) == operand</c>, <c>masksselect</c> is
        /// <c>(value &amp; operand) != 0</c>, <c>notmask</c> is <c>(value &amp; operand) == 0</c> —
        /// and the privilege mask is the most famous use of those predicates, not their semantics.
        /// The counterproof is <c>systemuser.accessmode</c>: <c>masksselect 1</c> matches 1, 3 and
        /// 5, because each has bit 0 set, and nothing in answering it reads a privilege, a role or
        /// an entitlement.
        /// </para>
        ///
        /// <para>
        /// <b>And why <c>masksselect</c> joined them in ADO-2500 rather than in ADO-2346.</b>  It
        /// was listed as a deliberate refusal on a FetchXML measurement — HTTP 400 <c>Unknown
        /// Condition Operator</c> on every spelling — and that measurement was true and did not
        /// support the conclusion drawn from it: the QueryExpression probe of 17 September 2026
        /// found the server <b>accepts</b> <c>ConditionOperator.MasksSelect</c> and answers it as
        /// <c>(value &amp; operand) != 0</c>.  The two measurements agree; what they say together is
        /// that the operator exists server-side and has no FetchXML grammar, which is a fact about a
        /// frontend and not a gap in coverage.  <c>FetchXmlOperatorMap</c> carries it, and this
        /// roster counts the operator as covered because <c>QueryExpression</c> reaches it.
        /// </para>
        ///
        /// <para>
        /// <b>Why the two <c>equaluseroruserhierarchy*</c> ones are here now.</b>  They stood out
        /// of this list while ADO-2326 registered their seven siblings, and the reason recorded at
        /// the time — "answering them means walking the business-unit hierarchy" — named the wrong
        /// tree.  The hierarchy these two operators answer for is <c>systemuser</c>'s: the caller
        /// and every user <i>below</i> them in the manager chain, plus the teams that whole set
        /// belongs to.  ADO-2336 resolved exactly that set, once per plan, under
        /// <see cref="OperatorContextRequirement.UserHierarchy"/>; what was missing was never an
        /// implementation but the hierarchy, and it was never the business unit's.
        /// </para>
        ///
        /// <para>
        /// <b>And why the one that is left is not here.</b>  <c>ChildOf</c> is not unfinished: it
        /// is out for a mechanism somebody measured, and the mechanism is a refusal of USE rather
        /// than of the name.  FetchXML parses the spelling and the platform then rejects the
        /// attribute ("The parentbusinessunitid attribute is not a valid attribute for the child-of
        /// operator", ADO-2307: eight rejections out of eight); <c>QueryExpression</c>, at the

        /// standard queries. It is for internal crm infrastructure use only via OutlookSync

        /// operator, not an unknown one — and there is still no observed behaviour for an evaluator
        /// to mirror, since the platform declines every ordinary query naming it.  It is a
        /// deliberate non-operator, not an unfinished one.

        [Fact]
        public void ConditionOperator_MatchesThePinnedSdkInventory()
        {
            var actual = Enum.GetNames(typeof(ConditionOperator))
                .Select(name => (Name: name, Value: (int)(ConditionOperator)Enum.Parse(typeof(ConditionOperator), name)))
                .ToArray();

            // The pin is only visible as an inventory, for the reason the class doc states — but
            // the assembly the inventory was read from is not, so it is named here.
            Assert.Equal("Microsoft.Xrm.Sdk", typeof(ConditionOperator).Assembly.GetName().Name);

            Assert.Equal(SdkOperatorCount, actual.Length);
            Assert.Equal(ExpectedSdkInventory, actual);
        }

        [Fact]
        public void ConditionOperator_ValuesAreContiguousFromZero()
        {
            var values = Enum.GetValues(typeof(ConditionOperator))
                .Cast<ConditionOperator>()
                .Select(v => (int)v)
                .OrderBy(v => v)
                .ToArray();

            Assert.Equal(Enumerable.Range(0, SdkOperatorCount).ToArray(), values);
        }

        [Fact]
        public void OperatorIdentity_CoversTheWholeSdkInventoryAndNothingElse()

            var expected = ExpectedSdkInventory

        }

        /// <summary>
        /// The coverage claim of ADO-2500, measured the only way that cannot drift: enumerate
        /// <see cref="ConditionOperator"/> by reflection off the pinned SDK assembly, turn each
        /// member into its canonical identity with the <b>production frontend's own rule</b>, and
        /// ask a registry built by <see cref="OperatorEvaluatorBootstrapper.RegisterAll"/> whether
        /// it answers.  88 of the 89 must.
        ///
        /// <para>
        /// Three ways of getting the same number are deliberately not used here.  Counting the
        /// registry's keys would count anything registered under a spelling no SDK member carries
        /// — the exact defect ADO-2286 removed — and would still report the right total the day an
        /// alias crept back in.  Counting distinct evaluator classes would undercount: one
        /// <c>CalendarPeriodEvaluator</c> serves nine operators.  And asserting a hand-written list
        /// of names would freeze the list rather than the engine: the list would be edited to match
        /// whatever the bootstrapper happened to do, which is how a freeze stops freezing.
        /// </para>
        ///
        /// <para>
        /// The inventory guards come first on purpose.  If the pin moved and the enum grew a 90th
        /// member, "88 are covered" would still be true and would still mean something different,
        /// so the test refuses to interpret the count until it has confirmed the denominator.
        /// </para>
        /// </summary>
        [Fact]
        public void RegisterAll_CoversExactlyEightyEightOfTheSdksEightyNineOperators()
        {
            var members = Enum.GetValues(typeof(ConditionOperator)).Cast<ConditionOperator>().ToArray();

            // The denominator, before anything is read into the numerator.
            Assert.Equal(SdkOperatorCount, members.Length);
            Assert.Equal(
                Enumerable.Range(0, SdkOperatorCount).ToArray(),
                members.Select(m => (int)m).OrderBy(v => v).ToArray());

            var registry = BootstrappedRegistry();

            var covered = members
                .Where(m => registry.IsSupported(CanonicalIdentityAsProductionDerivesIt(m)))
                .Select(m => m.ToString())
                .OrderBy(n => n, StringComparer.Ordinal)
                .ToArray();

            var expected = ExpectedCoverageRoster
                .Select(canonical => members.Single(m => OperatorIdentity.Of(m) == canonical).ToString())
                .ToArray();

            string diagnosis =
                $"Expected {ExpectedCoveredOperatorCount} of {SdkOperatorCount} ConditionOperator members to " +
                $"resolve in the bootstrapped registry, but {covered.Length} did." +
                Listing("expected but not resolving", expected.Except(covered)) +
                Listing("resolving but not expected", covered.Except(expected));

            Assert.True(covered.Length == ExpectedCoveredOperatorCount, diagnosis);

            // Same claim, said by name: 88 of a different 88 would pass the count alone.
            Assert.True(!expected.Except(covered).Any() && !covered.Except(expected).Any(), diagnosis);
        }

        /// <summary>
        /// The registration claim of ADO-2346 and ADO-2500, said on its own so a regression names
        /// the operator rather than only moving the count: the three bitwise operators resolve under
        /// the canonical identities <c>mask</c>, <c>masksselect</c> and <c>notmask</c> and under
        /// <b>nothing else</b>, each to the evaluator written for it and not to a borrowed one.
        ///
        /// <para>
        /// The "nothing else" half is the point the count cannot make, and it is the half ADO-2500
        /// put weight on.  A registry entry under a FetchXml spelling would be a second place
        /// coverage is declared — the defect ADO-2286 removed — and it is unnecessary for
        /// <c>not-mask</c>, which reaches <c>notmask</c> through
        /// <see cref="OperatorIdentity.Normalize"/>; for <c>masksselect</c> it would be worse than
        /// unnecessary, because FetchXML has no spelling for that operator at all, so a key here
        /// would claim a door the server does not open.  The last block asserts that no spelling of
        /// it resolves.
        /// </para>
        ///
        /// <para>
        /// <b>Each evaluator is asserted by TYPE and not only by presence.</b>  <c>mask</c> and
        /// <c>masksselect</c> differ by one clause and share a base class, so a registration that
        /// bound <c>mask</c> to <see cref="MasksSelectEvaluator"/> would answer every single-bit
        /// query correctly — which is the shape of the defect ADO-2500 repaired, and the reason this
        /// test names the types.
        /// </para>
        /// </summary>
        [Fact]
        public void RegisterAll_RegistersTheBitwiseTrioUnderItsCanonicalIdentitiesAndNothingElse()
        {
            var registry = BootstrappedRegistry();

            Assert.IsType<MaskEvaluator>(registry.Resolve("mask"));
            Assert.IsType<MasksSelectEvaluator>(registry.Resolve("masksselect"));
            Assert.IsType<NotMaskEvaluator>(registry.Resolve("notmask"));

            foreach (string canonical in new[] { "mask", "masksselect", "notmask" })
            {
                Assert.Equal(OperatorSupportStatus.Supported, registry.SupportOf(canonical).Status);
                Assert.Null(registry.SupportOf(canonical).Reason);

                // Neither of the three asks for anything the row cannot supply.
                Assert.Equal(OperatorContextRequirement.None, registry.ContextRequirementsOf(canonical));
            }

            // The identities are the ones production derives, and they are the SDK member names
            // lowercased — not a spelling invented for the registry.
            Assert.Equal("mask", CanonicalIdentityAsProductionDerivesIt(ConditionOperator.Mask));
            Assert.Equal("masksselect", CanonicalIdentityAsProductionDerivesIt(ConditionOperator.MasksSelect));
            Assert.Equal("notmask", CanonicalIdentityAsProductionDerivesIt(ConditionOperator.NotMask));

            // The FetchXml spelling of notmask arrives at the same entry without an alias existing.
            Assert.Equal("notmask", FetchXmlOperatorMap.Resolve("not-mask"));
            Assert.Same(registry.Resolve("notmask"), registry.Resolve(FetchXmlOperatorMap.Resolve("not-mask")));

            // ...and masksselect arrives from nowhere on that side: no spelling of it resolves, so
            // there is no FetchXml key for the registry to have been given.
            foreach (string spelling in MasksSelectSpellings)
                Assert.False(FetchXmlOperatorMap.TryResolve(spelling, out _), spelling);
        }

        /// <summary>
        /// Every spelling of <c>MasksSelect</c> a FetchXml caller might write, including the two
        /// this engine's own normalisation would otherwise reach (<c>MasksSelect</c> as the SDK
        /// spells it, and the hyphenated title case): all of them collapse to the canonical
        /// <c>masksselect</c> under <see cref="OperatorIdentity.Normalize"/>, and all of them must
        /// be refused by the FetchXml frontend.
        /// </summary>
        public static readonly string[] MasksSelectSpellings =
        {
            "masks-select", "masksselect", "masks_select", "MasksSelect", "Masks-Select",
        };

        /// <summary>
        /// The separation ADO-2500 established, in one place: <c>masksselect</c> is
        /// <b>supported</b> — the registry answers it, and a <c>QueryExpression</c> reaches it —
        /// and it is <b>unreachable from FetchXml</b>, in every spelling that normalises to it.
        ///
        /// <para>
        /// The two halves have to be asserted together, because each alone reads as the old state:
        /// "supported" alone would be satisfied by an engine that also translated
        /// <c>masks-select</c> into a plan Dataverse would refuse, and "refused by FetchXml" alone
        /// was true before this node and meant the opposite thing.
        /// </para>
        /// </summary>
        [Fact]
        public void MasksSelect_IsSupportedByQueryExpressionAndRefusedByEverySpellingOfFetchXml()
        {
            var registry = BootstrappedRegistry();

            Assert.True(registry.IsSupported("masksselect"));
            Assert.Equal(OperatorSupportStatus.Supported, registry.SupportOf("masksselect").Status);

            // Through the real chain, on the QueryExpression side: accepted, no refusal at all.
            Assert.Null(RefusalFrom(QueryExpressionPlan(ConditionOperator.MasksSelect, new[] { "6" })));

            foreach (string spelling in MasksSelectSpellings)
            {
                Assert.Equal("masksselect", OperatorIdentity.Normalize(spelling));

                Assert.False(FetchXmlOperatorMap.TryResolve(spelling, out _), spelling);
                Assert.False(FetchXmlOperatorMap.IsSupported(spelling, registry), spelling);

                // Resolve keeps throwing, and keeps the RAW spelling the caller wrote: a refusal
                // that renamed the operator would send the reader looking for a keyword they never
                // typed.
                var fromResolve = Assert.Throws<NotSupportedQueryOperatorException>(
                    () => FetchXmlOperatorMap.Resolve(spelling));
                Assert.Equal(spelling, fromResolve.OperatorName);

                // ...and the refusal a FetchXml CALLER meets is raised at the boundary, carrying
                // the declaration rather than a bare "not supported".
                var atTheBoundary = Assert.Throws<NotSupportedQueryOperatorException>(
                    () => FetchXmlPlan(spelling, new[] { "6" }));

                Assert.Equal(spelling, atTheBoundary.OperatorName);
                Assert.Equal("statuscode", atTheBoundary.AttributeName);
                Assert.Equal(OperatorSupportStatus.DeliberatelyRejected, atTheBoundary.Status);
                Assert.False(string.IsNullOrWhiteSpace(atTheBoundary.Reason), spelling);
            }

            // The declaration is queryable on the canonical key, and it answers the other way for
            // childof — which HAS a FetchXml spelling and is refused for a different reason.
            Assert.True(FetchXmlOperatorMap.TryGetMissingFetchXmlGrammarReason("masksselect", out string? declared));
            Assert.False(string.IsNullOrWhiteSpace(declared));
            Assert.False(FetchXmlOperatorMap.TryGetMissingFetchXmlGrammarReason("childof", out string? none));
            Assert.Null(none);

            // The reason the caller gets is the declaration itself, not a sentence composed at the
            // throw site: one source, so a log line and the published matrix cannot disagree.
            var refusal = Assert.Throws<NotSupportedQueryOperatorException>(
                () => FetchXmlPlan("masks-select", new[] { "6" }));
            Assert.Equal(declared, refusal.Reason);
        }

        /// <summary>
        /// The other half of the same claim: after ADO-2500 the <b>only</b> operator the engine
        /// does not answer is <c>childof</c>, and it is
        /// <see cref="OperatorSupportStatus.DeliberatelyRejected"/> with the reason the registry
        /// declares — so there is no operator left that is merely not covered, and a second one
        /// appearing in either disposition turns this red.
        ///
        /// <para>
        /// <c>masksselect</c> was the other row until ADO-2500 and left the list by being
        /// <i>answered</i>, not reclassified: the FetchXML measurement it was refused on was real
        /// and said something narrower than it was read as saying — no FetchXML grammar, not no
        /// operator.
        /// </para>
        /// </summary>
        [Fact]
        public void RegisterAll_LeavesChildOfAsTheOnlyOperatorItDoesNotAnswer()
        {
            var registry = BootstrappedRegistry();

            var unsupported = OperatorIdentity.All
                .Where(key => !registry.IsSupported(key))
                .OrderBy(key => key, StringComparer.Ordinal)
                .ToArray();

            Assert.Equal(new[] { "childof" }, unsupported);

            Assert.All(unsupported, key =>
            {
                var support = registry.SupportOf(key);
                Assert.Equal(OperatorSupportStatus.DeliberatelyRejected, support.Status);
                Assert.False(string.IsNullOrWhiteSpace(support.Reason), key);
            });

            // Nothing is left in the "nobody has got to it" disposition: mask and notmask were the
            // last two, and ADO-2346 answered them rather than reclassifying them.
            Assert.Empty(OperatorIdentity.All
                .Where(key => registry.SupportOf(key).Status == OperatorSupportStatus.NotCovered));
        }

        ///
        /// <para>
        /// The second assertion is the point: it pins that <see cref="OperatorIdentity.Of"/> still

            return canonical;

        /// <summary>
        /// The five structural hierarchy operators of ADO-2337: registered under their canonical
        /// identity, bound to the evaluator written for each, declaring <b>no</b> execution-context
        /// requirement — and declaring, through
        /// <see cref="IHierarchyAwareConditionEvaluator"/>, the one thing they do need.
        ///
        /// <para>
        /// Both halves matter, and the first is the counter-intuitive one.  "Needs nothing from the
        /// execution context" is the right answer here: where a record sits in a tree has nothing
        /// to do with who is asking, and an operator of this family that declared a context
        /// requirement would make every hierarchy query read <c>usersettings</c> to no purpose.
        /// What it must not be read as is "answerable from the row alone" — which is why the
        /// capability is asserted beside it, and why it is a separate interface rather than a
        /// member of <see cref="OperatorContextRequirement"/>: that enum is the input of
        /// <c>MockQueryExecutionContextResolver.Resolve</c>, which never sees a condition.
        /// </para>
        ///
        /// <para>
        /// The shape validator is the third half: the pivot is a value the CONDITION carries, so
        /// "exactly one value, readable as an identifier" is a refusal no store can rescue and it
        /// belongs before the first row — for the reason <see cref="IConditionShapeValidator"/>
        /// states in full.
        /// </para>
        /// </summary>
        [Theory]
        [InlineData(ConditionOperator.Above, "above", typeof(AboveEvaluator))]
        [InlineData(ConditionOperator.AboveOrEqual, "aboveorequal", typeof(AboveOrEqualEvaluator))]
        [InlineData(ConditionOperator.Under, "under", typeof(UnderEvaluator))]
        [InlineData(ConditionOperator.UnderOrEqual, "underorequal", typeof(UnderOrEqualEvaluator))]
        [InlineData(ConditionOperator.NotUnder, "notunder", typeof(NotUnderEvaluator))]
        public void StructuralHierarchyOperators_DeclareTheTraversalCapabilityAndNoContextRequirement(
            ConditionOperator op, string canonical, Type expectedEvaluator)
        {
            var registry = BootstrappedRegistry();

            Assert.Equal(canonical, OperatorIdentity.Of(op));
            Assert.True(OperatorIdentity.IsCanonical(canonical));
            Assert.True(registry.IsSupported(canonical));

            var evaluator = registry.Resolve(canonical);
            Assert.IsType(expectedEvaluator, evaluator);

            // The capability, read through the same class that reads the context requirement.
            Assert.True(OperatorCapabilities.RequiresHierarchy(evaluator));
            Assert.IsAssignableFrom<IHierarchyAwareConditionEvaluator>(evaluator);
            Assert.IsAssignableFrom<IConditionShapeValidator>(evaluator);

            Assert.Equal(OperatorContextRequirement.None, registry.ContextRequirementsOf(canonical));
        }

        /// <summary>
        /// The capability is declared by those five and by nobody else — in particular not by the
        /// two hybrid identity operators, which answer about the caller's hierarchy and read it off
        /// the execution context.  Measured off the registry, so an eleventh hierarchy registration
        /// cannot slip in without this saying so.
        /// </summary>
        [Fact]
        public void TheStructuralHierarchyFamilyIsFiveOperators()
        {
            var registry = BootstrappedRegistry();

            var family = OperatorIdentity.All

            Assert.False(OperatorCapabilities.RequiresHierarchy(registry.Resolve("equaluseroruserhierarchy")));
            Assert.False(OperatorCapabilities.RequiresHierarchy(registry.Resolve("equaluseroruserhierarchyandteams")));

        /// <summary>
        /// The two hybrid requirements are two bits, and this is where the separation is frozen:
        /// 128 for the caller's hierarchy, 64 for the caller's own teams, and neither implying the
        /// other.
        ///
        /// <para>
        /// Folding them together keeps every query running and answers one of the two families
        /// wrongly — <c>equaluserteams</c> enumerating a hierarchy it never reads, or the hierarchy
        /// answering with the caller's teams alone.  A wrong set of the right shape is what no
        /// assertion on cardinality catches, so the bits themselves are asserted.
        /// </para>
        /// </summary>
        [Fact]
        public void TheHybridRequirementIsBit128AndUserTeamsStaysBit64()
        {
            Assert.Equal(128, (int)OperatorContextRequirement.UserHierarchy);
            Assert.Equal(64, (int)OperatorContextRequirement.UserTeams);

            var registry = BootstrappedRegistry();

            foreach (string canonical in new[] { "equaluseroruserhierarchy", "equaluseroruserhierarchyandteams" })
            {
                var declared = registry.ContextRequirementsOf(canonical);

                Assert.Equal(OperatorContextRequirement.UserHierarchy, declared);
                Assert.False((declared & OperatorContextRequirement.UserTeams) == OperatorContextRequirement.UserTeams);
            }

            // ...and the team-only operator has not acquired the hierarchy along the way.
            var teamsOnly = registry.ContextRequirementsOf("equaluserteams");
            Assert.Equal(OperatorContextRequirement.UserTeams, teamsOnly);
            Assert.False((teamsOnly & OperatorContextRequirement.UserHierarchy) == OperatorContextRequirement.UserHierarchy);
        }

        /// <summary>
        /// The values a parity case puts in its condition.  A generic "1" used to serve every
        /// operator, and since ADO-2291 it cannot: the shape of a condition is now validated
        /// before the first row is read, so an operator that wants a date or a count of values
        /// other than one refuses the probe itself — and the theory would then be comparing two
        /// frontends on a malformed query instead of on the operator contract.  So the sample
        /// value carries the type and the arity its operator asks for.
        /// </summary>
        private static string[] SampleValuesFor(ConditionOperator op)
        {
            switch (op)
            {
                // The four explicit-date operators compare against a date named in the condition,
                // and ExplicitDateEvaluator.ValidateCondition refuses anything that names no
                // instant.  The relative date operators are not here: their parameter is a count,
                // and "1" is a valid one.
                case ConditionOperator.On:
                case ConditionOperator.NotOn:
                case ConditionOperator.OnOrBefore:
                case ConditionOperator.OnOrAfter:
                    return new[] { "2026-01-15T00:00:00Z" };

                case ConditionOperator.Null:
                case ConditionOperator.NotNull:
                    return new string[0];

                case ConditionOperator.Between:
                case ConditionOperator.NotBetween:
                    return new[] { "1", "2" };

                // The fiscal trio names a COORDINATE and carries two values, in the SDK's
                // documented order: the period number first, the fiscal year second (ADO-2316).
                // Until ADO-2316 registered them the arity did not matter — an unregistered
                // operator is refused before any shape is looked at — but a registered one is
                // validated before the first row, and a single value makes
                // FiscalPeriodAndYearEvaluator.ValidateCondition throw InvalidOperationException,
                // which RefusalFrom does not catch and which would fail the theory rather than
                // answer it.
                case ConditionOperator.InFiscalPeriodAndYear:
                case ConditionOperator.InOrBeforeFiscalPeriodAndYear:
                case ConditionOperator.InOrAfterFiscalPeriodAndYear:
                    return new[] { "1", "2026" };

                // One value, but a year and not a count: InFiscalYearEvaluator refuses anything
                // outside 1-9999, and a plausible year says what the operator is for.
                case ConditionOperator.InFiscalYear:
                    return new[] { "2026" };

                // The five structural hierarchy operators name a RECORD — the pivot the tree is
                // walked from — so their single value has to read as an identifier (ADO-2337).
                // "1" would be refused by their shape validator before the first row, and the
                // theory would then be comparing two frontends on a malformed query instead of on
                // the operator contract.
                case ConditionOperator.Above:
                case ConditionOperator.AboveOrEqual:
                case ConditionOperator.Under:
                case ConditionOperator.UnderOrEqual:
                case ConditionOperator.NotUnder:
                    return new[] { "8f14e45f-ceea-467a-9575-1c6aefd5e402" };

                default:
                    return new[] { "1" };
            }
        }

        {
            var spelled = FetchXmlSpellings.Select(s => s.Operator.ToString()).Distinct().ToArray();
            var unspellable = OperatorsWithoutAFetchXmlSpelling.Select(op => op.ToString()).ToArray();

            var covered = spelled
                .Concat(unspellable)
                .OrderBy(n => n, StringComparer.Ordinal)
                .ToArray();

            var expected = ExpectedSdkInventory
                .Select(e => e.Name)
                .OrderBy(n => n, StringComparer.Ordinal)
                .ToArray();

            Assert.Equal(expected, covered);
            Assert.Empty(spelled.Intersect(unspellable));

            // And the declaration behind the second list is the production one, not a copy: every
            // operator in it must be one FetchXmlOperatorMap itself says has no grammar.
            Assert.All(
                OperatorsWithoutAFetchXmlSpelling,
                op => Assert.True(
                    FetchXmlOperatorMap.TryGetMissingFetchXmlGrammarReason(OperatorIdentity.Of(op), out _),
                    op.ToString()));
        }

        [Theory]
        [MemberData(nameof(FetchXmlSpellingTable))]
        public void BothFrontends_ProduceTheSameIdentity(ConditionOperator op, string fetchXmlOperator)
        {
            Assert.Equal(OperatorIdentity.Of(op), FetchXmlOperatorMap.Resolve(fetchXmlOperator));
        }

        [Theory]
        [MemberData(nameof(FrontendParityCases))]
        public void BothFrontends_AgreeOnSupportAndOnRefusal(
            ConditionOperator op, string fetchXmlOperator, string[] values)
        {
            var registry = BootstrappedRegistry();

            bool supportedViaQueryExpression = registry.IsSupported(OperatorIdentity.Of(op));
            bool supportedViaFetchXml = FetchXmlOperatorMap.IsSupported(fetchXmlOperator, registry);

            Assert.Equal(supportedViaQueryExpression, supportedViaFetchXml);

            // Same answer from the shared rejection point whichever door the query came through:
            // the same operator in the same exception when unsupported, null on both when not.
            Assert.Equal(
                RefusalFrom(QueryExpressionPlan(op, values)),
                RefusalFrom(FetchXmlPlan(fetchXmlOperator, values)));
        }

        [Fact]
        public void ProductionChain_AcceptsContainValuesIdenticallyOnBothFrontends()
        {
            // The chain production builds: bootstrapped registry → InMemoryExecutor → frontends
            // constructed with no arguments (PluginRunnerService, FrameworkOrganizationServiceAdapter).
            // ADO-2286 asserted here that this chain refused contain-values; ADO-2290 registered an
            // evaluator for it, so the chain must now accept it — through both doors, or neither.
            var values = SampleValuesFor(ConditionOperator.ContainValues);

            Assert.Null(RefusalFrom(QueryExpressionPlan(ConditionOperator.ContainValues, values)));
            Assert.Null(RefusalFrom(FetchXmlPlan("contain-values", values)));
        }

        /// <summary>
        /// The refusal half of the same claim, kept on an operator that still has no evaluator:
        /// an engine that accepts everything would pass the test above while having stopped
        /// refusing anything.
        /// </summary>
        [Theory]
        // The row is the one operator nothing is coming for, which is what makes it last.
        // Above and Under stood on the first and last rows until ADO-2337 registered the five
        // structural hierarchy operators — and ThisFiscalYear and LastXFiscalPeriods stood on two
        // more until ADO-2316 registered the fiscal family: rows lost in two nodes, each chosen
        // because some brief had put its family outside its perimeter, which is a fact about a plan
        // and not about the operator.  Mask and NotMask were the same kind of bet and went the same
        // way in ADO-2346: they were kept here on the belief that answering them needed Dataverse's
        // access-mask model, and they need nothing of the sort — each is one bitwise clause over the
        // integer value a row holds for any integer attribute of any table (`mask` is
        // `(value & operand) == operand`, as ADO-2500 measured), and the privilege mask is those
        // predicates' most famous use, not their meaning.
        //
        // ONE ROW IS LEFT, and it does not depend on anyone's perimeter.  ChildOf is marked "for
        // internal use only" by the SDK reference and the platform refuses every ordinary query
        // naming it — through FetchXML as an attribute error and through QueryExpression, at the
        // operator's own arity of zero values, by naming the reservation outright (ADO-2307,
        // ADO-2498) — so there is no observed behaviour an evaluator could mirror.  It is a
        // deliberate non-operator and not an unfinished one, and that is why it did NOT come along
        // with the hierarchy family it used to be listed beside.
        //
        // MasksSelect stood on the other row until ADO-2500, and it was the third bet of this kind
        // in this comment: it was listed here on the FetchXML measurement alone, and the
        // QueryExpression probe found the server ACCEPTS it.  Both frontends no longer agree about
        // it and must not — the operator is supported and has no FetchXML grammar — so its claim
        // moved to MasksSelect_IsSupportedByQueryExpressionAndRefusedByEverySpellingOfFetchXml,
        // which asserts the divergence instead of the parity.
        //
        // LastXDays stood here before all of them and was the wrong kind of choice — unregistered
        // on the ADO-2291 branch, but registered by ADO-2292 on its own, so the freeze went red
        // only once the two were integrated, and neither branch could see it alone.
        [InlineData(ConditionOperator.ChildOf, "child-of", "childof")]
        public void ProductionChain_RefusesAnUnregisteredOperatorIdenticallyOnBothFrontends(
            ConditionOperator op, string fetchXmlOperator, string canonical)
        {
            var values = SampleValuesFor(op);

            var qeRefusal = RefusalFrom(QueryExpressionPlan(op, values));
            var fetchRefusal = RefusalFrom(FetchXmlPlan(fetchXmlOperator, values));

            Assert.Equal($"{canonical} on statuscode", qeRefusal);
            Assert.Equal(qeRefusal, fetchRefusal);
        }

        /// <summary>
        /// The refusal witness that no future node can register away: a name that is not a member
        /// of the SDK enum at all — <c>(ConditionOperator)9999</c> on the QueryExpression side, an
        /// invented keyword on the FetchXml one.
        ///
        /// <para>
        /// <b>Why this exists beside the theory above.</b>  Every witness that theory has ever used
        /// was an operator of the inventory that happened to have no evaluator yet, and three of
        /// them have since been registered — twice by a sibling node of the same swarm, so the
        /// freeze went red only at integration.  The two rows left are durable on the merits, but
        /// "durable on the merits" is a judgement, and this one is not: the identity space is
        /// <i>exactly</i> the pinned enum, so a member outside it cannot become supported without
        /// the pin moving, which <see cref="ConditionOperator_MatchesThePinnedSdkInventory"/>
        /// already refuses.
        /// </para>
        ///
        /// <para>
        /// The refusal lands in a different place on each side, and that is the point rather than
        /// an asymmetry to paper over: the FetchXml frontend cannot even name the operator, so it
        /// refuses while building the plan, whereas a cast integer survives translation and is
        /// refused by <see cref="OperatorIdentity.Of"/> inside it.  Both raise the same exception
        /// type carrying the same spelling the caller wrote.
        /// </para>
        /// </summary>
        [Fact]
        public void ProductionChain_RefusesANameOutsideTheSdkInventoryOnBothFrontends()
        {
            var outsideTheEnum = (ConditionOperator)9999;

            var qeEx = Assert.Throws<NotSupportedQueryOperatorException>(
                () => QueryExpressionPlan(outsideTheEnum, new[] { "1" }));
            Assert.Equal("9999", qeEx.OperatorName);

            var fetchEx = Assert.Throws<NotSupportedQueryOperatorException>(
                () => FetchXmlPlan("frobnicate", new[] { "1" }));
            Assert.Equal("frobnicate", fetchEx.OperatorName);

            // Neither spelling is a registry key, and neither resolves to one.
            var registry = BootstrappedRegistry();
            Assert.False(registry.IsSupported("9999"));
            Assert.False(registry.IsSupported("frobnicate"));
            Assert.False(OperatorIdentity.TryCanonicalize("frobnicate", out _));
        }

        // -----------------------------------------------------------------------
        // Helpers — the production chain, assembled exactly as production assembles it
        // -----------------------------------------------------------------------

        private static ConditionEvaluatorRegistry BootstrappedRegistry()
        {
            var registry = new ConditionEvaluatorRegistry();
            OperatorEvaluatorBootstrapper.RegisterAll(registry);
            return registry;
        }

        private static MockQueryPlan QueryExpressionPlan(ConditionOperator op, string[] values)
        {
            var qe = new QueryExpression("account");
            qe.Criteria.AddCondition("statuscode", op, values);
            return new QueryExpressionFrontend().BuildPlan(qe);
        }

        private static MockQueryPlan FetchXmlPlan(string fetchXmlOperator, string[] values)
        {
            // One value is the attribute form and any other count is the <value> child form:
            // the two are the same condition to the frontend, but only the second can carry
            // none or two.
            string condition = values.Length == 1
                ? $"<condition attribute=\"statuscode\" operator=\"{fetchXmlOperator}\" value=\"{values[0]}\"/>"
                : $"<condition attribute=\"statuscode\" operator=\"{fetchXmlOperator}\">"
                  + string.Concat(values.Select(v => $"<value>{v}</value>"))
                  + "</condition>";

            string xml =
                "<fetch><entity name=\"account\"><filter>" + condition + "</filter></entity></fetch>";

            return new FetchXmlFrontend().BuildPlan(new FetchExpression(xml));
        }

        /// <summary>
        /// Runs the plan through the shared rejection point and returns the refusal as
        /// "operator on attribute", or <c>null</c> when the plan was accepted.
        ///
        /// <para>
        /// A hierarchy that cannot be resolved is a refusal of a different kind and is reported as
        /// one rather than escaping: the store here is empty, so the five structural operators of
        /// ADO-2337 cannot name a target entity and are refused before the first row — on both
        /// frontends, identically, which is exactly the claim the callers are making.  Letting it
        /// escape would fail the parity theory instead of answering it.
        /// </para>
        /// </summary>
        private static string? RefusalFrom(MockQueryPlan plan)
        {
            var executor = new InMemoryExecutor(BootstrappedRegistry());

            try
            {
                executor.Execute(plan, new EmptyDataSource()).ToList();
                return null;
            }
            catch (NotSupportedQueryOperatorException ex)
            {
                return $"{ex.OperatorName} on {ex.AttributeName}";
            }
            catch (MockHierarchyResolutionException ex)
            {
                return $"unresolvable hierarchy: {ex.Message}";
            }
        }

        private sealed class EmptyDataSource : IDataSource
        {
            public IEnumerable<Entity> GetEntities(string logicalName) => new List<Entity>();

            public Entity GetById(string logicalName, Guid id) => null!;
        }
    }
