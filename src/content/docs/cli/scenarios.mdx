# Scenario Files

A **scenario** is a JSON document that describes one operation: which plugin runs, the execution
context it runs in, the data it is allowed to read, and — optionally — the exception it is expected
to throw. You hand it to [`xg run`](/cli/reference/run/) with `--scenario`, and the FrameworkHost
builds the whole `IPluginExecutionContext` from it.

This page is the canonical reference for that document. A starting template for a real assembly can
be produced with [`xg generate-scenario`](/cli/reference/generate-scenario/); everything below is
what you edit afterwards.

The scenario is **input, and it is never rewritten**. The host reads it when the run starts and
builds the run's state from it in memory; every record the plugin creates, updates or deletes changes
that state, for that run only. Nothing is written back to the file, so two runs of the same scenario
start from the same input, whatever the first one did. What each write does to the run's state is
described in [What the run does with its writes](#what-the-run-does-with-its-writes).

## Minimum shape

Four keys are enough to run a plugin:

```json
{
  "scenarioName": "Short description of the operation",
  "pluginAssemblyName": "MyCompany.Plugins.dll",
  "pluginTypeName": "MyCompany.Plugins.Account.ValidateAccount",
  "executionContext": {
    "messageName": "Create",
    "primaryEntityName": "account",
    "primaryEntityId": "00000000-0000-0000-0000-000000000001",
    "stage": 20,
    "mode": 0,
    "inputParameters": {
      "Target": {
        "logicalName": "account",
        "id": "00000000-0000-0000-0000-000000000001",
        "attributes": { }
      }
    }
  }
}
```

| Key | What it is |
|---|---|
| `scenarioName` | A human label. It appears in the run output and is never interpreted. |
| `pluginAssemblyName` | The assembly the scenario was written against — documentation for the reader; the assembly actually loaded is the one `xg run -a` points at. |
| `pluginTypeName` | The fully-qualified plugin type the scenario was written against; the type actually executed is the one `xg run -t` names. |
| `executionContext` | Everything the plugin sees through `IPluginExecutionContext`. |

Inside `executionContext`, three fields carry most of the meaning:

- **`messageName`** — the Dataverse message: `Create`, `Update`, `Delete`, `Retrieve`,
  `RetrieveMultiple`, or a Custom API message (see [Custom API scenarios](#custom-api-scenarios)).
  It is the name your plugin reads to decide whether it should act at all.
- **`stage`** — the pipeline stage: `10` PreValidation, `20` PreOperation, `40` PostOperation. The
  main operation of a Custom API is stage `30`.
- **`inputParameters.Target`** — the record the message carries. For `Create` and `Update` it is the
  entity being written, and its `attributes` object is what your plugin reads. For `Delete` it is
  normally an `EntityReference` instead.

`mode` is `0` for synchronous and `1` for asynchronous. `depth`, `userId`, `initiatingUserId`,
`organizationId`, `businessUnitId`, `correlationId`, `sharedVariables` and `outputParameters` are
accepted too, and default to sensible values when omitted.

## Attribute value typing

Inside any `attributes` object, value typing must be explicit or the framework misreads it. This is
the single most common source of scenario errors:

- **Plain values** (string, number, bool) are written directly — `"name": "Contoso Ltd"`,
  `"revenue": 1000000`, `"creditonhold": false`.
- **OptionSet / Picklist** is `{ "value": X }` — never the bare number. The tag
  `"type": "OptionSetValue"` is optional: `{ "type": "OptionSetValue", "value": X }` reads the same.
- **Money** is `{ "type": "Money", "value": X }`, where `X` may be an integer or a decimal. The
  `"type": "Money"` tag is what makes it Money: without it, `{ "value": X }` stays an OptionSet.
  With the current `xg` release the tag is honoured **only in the root-level
  [`entities`](#retrievemultiple--the-root-level-entities-key) seed**, which the CLI hands to the
  host as written; see the caution below.
- **EntityReference / lookup** is `{ "logicalName": "...", "id": "...", "name": "..." }`, where
  `name` is optional.
- **GUIDs must be valid hexadecimal.** An id containing a non-hex character — an `x`, a `g`, a typo
  — fails to parse inside an `EntityReference` and takes the whole scenario down with it.

```json
{
  "attributes": {
    "name": "Contoso Ltd",
    "revenue": 1000000,
    "statuscode": { "value": 2 },
    "primarycontactid": {
      "logicalName": "contact",
      "id": "00000000-0000-0000-0000-0000000000c1",
      "name": "Alex Taylor"
    }
  }
}
```

:::caution Where the Money tag is recognised
The CLI reads `Target`, the rest of `inputParameters`, `preEntityImages`, `postEntityImages` and
`organizationServiceMock` and writes them out again before handing them to the host, and the current
`xg` release does not carry the `"type": "Money"` tag through that step. Use the tag only on records
in the root-level `entities` seed; elsewhere, do not rely on it to produce a Money value.
:::

## Supplying the data the code reads

When the plugin reads other records while it runs, those records are described in the scenario — and
there are **two distinct mechanisms**, one per message. Using the wrong one is the second most
common mistake, because both "work" in the sense that the JSON parses and neither returns what you
expected.

| The plugin calls | You describe it in | Where the attributes go |
|---|---|---|
| `Retrieve` (one record, by id) | `organizationServiceMock.retrieveResponses` — or a record of the root-level `entities` seed with that id | **Nested** under an `attributes` object in `retrieveResponses`; **directly on the entity object** in `entities` |
| `RetrieveMultiple` (a query) | a **root-level** `entities` key, sibling of `executionContext` | **Directly on the entity object** |

### `Retrieve` — `organizationServiceMock.retrieveResponses`

Each entry pairs the call to match (`request`) with the record to hand back (`response`). An entry
matches on `entityName` **and** `id`; `request.columnSet` does not take part in the match, and can be
omitted:

```json
{
  "organizationServiceMock": {
    "retrieveResponses": [
      {
        "request": {
          "entityName": "contact",
          "id": "00000000-0000-0000-0000-0000000000c1",
          "columnSet": ["fullname", "emailaddress1"]
        },
        "response": {
          "logicalName": "contact",
          "id": "00000000-0000-0000-0000-0000000000c1",
          "attributes": {
            "fullname": "Alex Taylor",
            "emailaddress1": "alex.taylor@example.com"
          }
        }
      }
    ]
  }
}
```

#### How a `Retrieve` is answered

When the scenario answers a `Retrieve`, the host looks for the record in this order and stops at the
first source that has it:

1. **What the run itself did** — records the plugin created or updated during this run.
2. **`organizationServiceMock.retrieveResponses`** — the explicit responses above.
3. **The root-level `entities` seed** — see [the next section](#retrievemultiple--the-root-level-entities-key).
4. **The rest of the in-memory store.**

So **an explicit `retrieveResponses` entry wins over a seed record with the same `entityName` and
`id`**: declare a record in one place, or expect the response to be the one you see.

Whichever source answers, the record is **projected on the `ColumnSet` the plugin passes** — not on
the `columnSet` written in the scenario:

- columns the plugin did not ask for are not returned;
- the primary key (`<logicalName>id`) is always present;
- `new ColumnSet(true)` (all columns) returns every attribute the record has;
- an empty `ColumnSet` returns only the primary key.

A record that no source holds — or an id that is `Guid.Empty` — makes `Retrieve` throw the fault
Dataverse throws: a `FaultException<OrganizationServiceFault>` with error code `0x80040217`
(the record does not exist). A plugin that catches that fault sees what it would see in Dataverse.

Writes are visible to later reads within the same run: a `Retrieve` after the plugin's `Update`
returns the updated values, and a `Retrieve` after a `Delete` of that record throws the same
not-found fault, even if `retrieveResponses` or the seed still describe it. This holds for the
records the scenario mocks and the ones the run creates, and always with `--data-source mock`. It
does **not** hold for a record that exists in Dataverse when the run reads live (`auto` and `live`
with a Pro license): see [Writes to live records (Pro)](#writes-to-live-records-pro).

### `RetrieveMultiple` — the root-level `entities` key

`entities` is **not** inside `organizationServiceMock`: it sits at the root of the document, next to
`executionContext`. It is grouped by logical name, and each record carries its attributes **directly
on the object** — the opposite of `retrieveResponses`:

```json
{
  "entities": {
    "contact": [
      {
        "id": "00000000-0000-0000-0000-0000000000c1",
        "fullname": "Alex Taylor",
        "emailaddress1": "alex.taylor@example.com",
        "statuscode": { "value": 1 },
        "creditlimit": { "type": "Money", "value": 5000.50 },
        "parentcustomerid": {
          "logicalName": "account",
          "id": "00000000-0000-0000-0000-000000000001"
        }
      }
    ]
  }
}
```

The CLI does not hand this list back verbatim: the host **applies the query itself** and returns
only the records that match. So **every field the query's filter or order references must be present
on the record**, or it is filtered out and your plugin sees an empty result it will not explain to
you.

The same records also answer a `Retrieve` by id, after any matching `retrieveResponses` entry (see
[How a `Retrieve` is answered](#how-a-retrieve-is-answered)).

**A malformed seed fails the run.** If the `entities` value cannot be parsed, or one of its records
or attribute values cannot be converted, the plugin is not run against a partial store: the run is
reported as failed and `xg run` exits with code `1`, whatever `expectedException` declares. Fix the
seed; a run that silently dropped it
would not be testing what you wrote.

## What the run does with its writes

Every write the plugin makes through `IOrganizationService` changes the **state of the run** — the
in-memory copy built from the scenario when the run starts — and nothing else: not the scenario
file, and not Dataverse. The next run starts again from the scenario as written.

Whether a record exists is decided by the same lookup that answers a `Retrieve` (see
[How a `Retrieve` is answered](#how-a-retrieve-is-answered)): what the run itself did,
`retrieveResponses`, the root-level `entities` seed, the rest of the in-memory store. A record that
none of them knows **does not exist, as in Dataverse**: an `Update` or a `Delete` of it fails, and no
record is made up to let the write through. If the plugin writes to a record that it did not create
itself, declare that record in `entities` or in `retrieveResponses`.

| Message | Effect on the run's state | Fault |
|---|---|---|
| `Create` | Adds the record. Later `Retrieve` and `RetrieveMultiple` calls in the run see it, when they are answered from the mock (always with `--data-source mock`; for live reads see [Writes to live records (Pro)](#writes-to-live-records-pro)). Without a declared id, a new one is generated. | `0x80040237` (duplicate key) when the declared id — the entity's `Id` or its `<logicalName>id` attribute — is already known to the run: created earlier in it, or declared in `retrieveResponses` or `entities`. |
| `Retrieve` | None: it reads. | `0x80040217` (does not exist) when no source has the record, the id is `Guid.Empty`, or the run deleted the record earlier. |
| `RetrieveMultiple` | None: it reads. As a mock read, it evaluates the query against the run's records — the `entities` seed, plus the records the run created or updated, minus the ones it deleted. A live `RetrieveMultiple` does not (see [Writes to live records (Pro)](#writes-to-live-records-pro)). | — |
| `Update` | Merges the attributes the plugin sent onto the record as `Retrieve` would return it, whichever source that is. Later reads see the merged record when they are answered from the mock (always with `--data-source mock`; for live reads see [Writes to live records (Pro)](#writes-to-live-records-pro)). | `0x80040217` when no source knows the record, the run deleted it earlier, or the id is `Guid.Empty`. |
| `Delete` | Removes the record for the rest of the run, for reads answered from the mock (always with `--data-source mock`; for live reads see [Writes to live records (Pro)](#writes-to-live-records-pro)), even if `retrieveResponses` or `entities` still describe it. | `0x80040217` when no source knows the record, the run already deleted it, or the id is `Guid.Empty`. |

**In mock reads, `retrieveResponses` does not feed `RetrieveMultiple`.** A record declared only in
`retrieveResponses` answers a `Retrieve` by id, but a query does not find it — until the plugin
updates that record in the run: from then on the merged record is part of the run's state, and
`RetrieveMultiple` sees it like any other. A record the plugin must find through a query belongs in
`entities`.

**`Execute` follows the same model.** `Execute` with a `CreateRequest`, `UpdateRequest`,
`DeleteRequest`, `RetrieveRequest` or `RetrieveMultipleRequest` is handed to `Create`, `Update`,
`Delete`, `Retrieve` and `RetrieveMultiple` respectively, on every license: same run state, same
faults. A custom `OrganizationRequest` still throws `NotImplementedException`.

Both faults are the ones Dataverse throws — in C#, `FaultException<OrganizationServiceFault>`, with
the error code in `Detail.ErrorCode` — so a plugin that catches them sees what it would see in
Dataverse. That C# notation is **not** the value to write in `typeName`: `expectedException`
compares the CLR type's full name exactly, and for this fault that name is the one below, to be
copied as it is:

```json
"expectedException": {
  "typeName": "System.ServiceModel.FaultException`1[[Microsoft.Xrm.Sdk.OrganizationServiceFault, Microsoft.Xrm.Sdk, Version=9.0.0.0, Culture=neutral, PublicKeyToken=31bf3856ad364e35]]"
}
```

The same `typeName` serves both `0x80040217` and `0x80040237`: `expectedException` matches the type
and, optionally, the message — not the error code.

### Writes to live records (Pro)

:::note[auto and live: writes stay in the run]
With `--data-source auto` or `live`, a Pro license and an active environment, the run can reach
records the scenario does not declare. Writes to them still never leave the run:

- **An `Update` or `Delete` of a record no source of the run knows asks Dataverse** whether it
  exists, with a read-only `Retrieve` (`ColumnSet(false)`, no columns). If it exists, the change is
  kept in the run's state only: **nothing is written to Dataverse**, in any mode.
- **If Dataverse answers that the record does not exist**, the plugin gets Dataverse's own fault.
  Any other failure of that check makes the record count as missing — fault `0x80040217` — with a
  warning in `auto`.
- **The run's tombstone wins over live only for writes.** After the run deletes a record, a later
  `Update` or `Delete` of the same record faults `0x80040217` without asking Dataverse.
- **Reads are not covered by the run's state for records Dataverse has.** In `auto` and `live` a
  `Retrieve` goes to Dataverse first, so after an `Update` or a `Delete` of a live record it returns
  the record as it is in Dataverse — the run's change is not visible to it.
- **`RetrieveMultiple` in live does not see the run's writes.** The same holds in `auto` whenever
  the live query is attempted: the result does not include the records the run created or updated,
  and still includes the ones it deleted, whether or not the record exists in Dataverse. A live
  query that fails does not fall back to the mock. This is a different rule from the per-record
  fallback of `Retrieve`: `Retrieve` goes to Dataverse first and falls back to the run's sources,
  `RetrieveMultiple` does not.
- **In `live`, `Update` and `Delete` still find the records the scenario declares**, while
  `Retrieve` does not read them: it answers from Dataverse only.

Without a Pro license or an active environment, and always with `--data-source mock`, Dataverse is
not asked: a record no source of the run knows faults `0x80040217`.
:::

## Pre-images

A pre-image is supplied through a root-level `preEntityImages` key, whose name must match the image
registered on the step — the same name the code reads:

```json
{
  "preEntityImages": {
    "PreImage": {
      "logicalName": "account",
      "id": "00000000-0000-0000-0000-000000000001",
      "attributes": {
        "name": "Contoso Ltd",
        "revenue": 900000
      }
    }
  }
}
```

```csharp
var preImage = (Entity)context.PreEntityImages["PreImage"];
```

`postEntityImages` works identically. Both keys are also accepted under `executionContext`; when the
same key appears in both places the **root-level one wins** and the CLI prints a warning saying so,
so pick one and keep it there.

## Custom API scenarios

A Custom API runs through the same pipeline, but its scenario differs from an entity plugin's in
three ways:

- **Message name**: `custom_<publisherprefix>_<ApiName>` — both the `custom_` segment and the
  publisher prefix are required, because the message name *is* the API's unique name.
- **No `Target`**: each declared request parameter is a direct key under `inputParameters`.
- **Primary entity**: `primaryEntityName` is the empty string `""` or omitted — a Custom API is
  global, not bound to a record. Do not substitute a placeholder such as `"none"`.

```json
{
  "scenarioName": "Custom API - validate an invitation code",
  "pluginAssemblyName": "MyCompany.Plugins.dll",
  "pluginTypeName": "MyCompany.Plugins.Api.ValidateInvitation",
  "executionContext": {
    "messageName": "custom_mycompany_ValidateInvitation",
    "primaryEntityName": "",
    "stage": 30,
    "mode": 0,
    "inputParameters": {
      "InvitationCode": "ABC-123",
      "RequestedBy": "alex.taylor@example.com"
    }
  }
}
```

Backing data works exactly as it does for a plugin: `retrieveResponses` and `entities` are read the
same way.

## Expecting the outcome

### Happy path

A scenario with no `expectedException` expects the plugin **not to throw**. Putting the pieces above
together:

```json
{
  "scenarioName": "Account create — the credit limit is applied",
  "pluginAssemblyName": "MyCompany.Plugins.dll",
  "pluginTypeName": "MyCompany.Plugins.Account.ApplyCreditLimit",
  "executionContext": {
    "messageName": "Create",
    "primaryEntityName": "account",
    "primaryEntityId": "00000000-0000-0000-0000-000000000001",
    "stage": 20,
    "mode": 0,
    "inputParameters": {
      "Target": {
        "logicalName": "account",
        "id": "00000000-0000-0000-0000-000000000001",
        "attributes": {
          "name": "Contoso Ltd",
          "revenue": 1000000,
          "primarycontactid": {
            "logicalName": "contact",
            "id": "00000000-0000-0000-0000-0000000000c1"
          }
        }
      }
    }
  },
  "organizationServiceMock": {
    "retrieveResponses": [
      {
        "request": {
          "entityName": "contact",
          "id": "00000000-0000-0000-0000-0000000000c1",
          "columnSet": ["fullname", "emailaddress1"]
        },
        "response": {
          "logicalName": "contact",
          "id": "00000000-0000-0000-0000-0000000000c1",
          "attributes": {
            "fullname": "Alex Taylor",
            "emailaddress1": "alex.taylor@example.com"
          }
        }
      }
    ]
  }
}
```

The run passes when the plugin completes without throwing, and `xg run` exits with code `0`.

### Expecting an exception

Rejection is behaviour too. Derive the negative case from the scenario above — same plugin, an input
the plugin is supposed to refuse — and declare what it must throw:

```json
{
  "scenarioName": "Account create — a negative revenue is rejected",
  "pluginAssemblyName": "MyCompany.Plugins.dll",
  "pluginTypeName": "MyCompany.Plugins.Account.ApplyCreditLimit",
  "executionContext": {
    "messageName": "Create",
    "primaryEntityName": "account",
    "primaryEntityId": "00000000-0000-0000-0000-000000000001",
    "stage": 20,
    "mode": 0,
    "inputParameters": {
      "Target": {
        "logicalName": "account",
        "id": "00000000-0000-0000-0000-000000000001",
        "attributes": {
          "name": "Contoso Ltd",
          "revenue": -1
        }
      }
    }
  },
  "expectedException": {
    "typeName": "Microsoft.Xrm.Sdk.InvalidPluginExecutionException",
    "messageContains": "Revenue cannot be negative"
  }
}
```

Four rules govern how that declaration is evaluated:

- **`typeName` is mandatory and fully qualified.** It is the exception's namespace *and* type name —
  `Microsoft.Xrm.Sdk.InvalidPluginExecutionException`, not `InvalidPluginExecutionException` — and
  the comparison is **exact**: no base classes, no case-insensitivity, no partial names. An
  `expectedException` whose `typeName` is **missing or empty matches nothing**, and the run fails;
  an unwritten assertion is never a green run.
- **The whole exception chain is examined, from the outermost exception inward** through
  `InnerException`. When a plugin catches a failure and rethrows it wrapped, the outer type is a
  legitimate thing to declare — you do not have to dig down to the root cause.
- **`messageContains` is optional, and is checked on the same link as the type.** It is an
  ordinal substring test on that exception's message. A link whose type matches but whose message
  does not is *not* the answer: the walk continues inward, because the same type can appear twice in
  one chain and only the inner one may carry the text you named. Omitting `messageContains` simply
  states no constraint on the message.
- **A satisfied expectation is a passing run.** `xg run` exits `0` and the run summary reports
  `Execution Succeeded!` followed by an `Expected Exception Matched:` line. That line restates the
  expectation you declared — the `typeName`, plus `(message contains: …)` when `messageContains` is
  set — and is the confirmation that the match happened. The summary does not print the thrown
  exception, its message or its stack trace.

The expectation covers the **plugin's own execution and nothing wider**. A failure to load the
assembly or to construct the plugin type is the harness being broken, and stays red whatever the
scenario declares.

### Expecting traces

`expectedTraceLog` is a list of strings the plugin is expected to have written through
`ITracingService.Trace`. It is an assertion, evaluated once the plugin's `Execute` has finished:

```json
"expectedTraceLog": [
  "Credit limit applied",
  "revenue=1000000"
]
```

These rules govern how the list is evaluated:

- **Each entry is an ordinal, case-sensitive substring.** An entry is satisfied when the message of
  **at least one** trace emitted by the plugin contains it. `"credit limit"` does not match a trace
  that reads `Credit limit applied`.
- **Only traces with source `Plugin` count.** Lines written by the framework and the host are not
  searched, and neither is the rendered `TraceLog` you read with `-v` or `-d`: its prefixes and
  timestamps are presentation, not the corpus. A host line that merely quotes your expected text
  never satisfies the entry on the plugin's behalf.
- **Order is not checked, and entries are independent.** The entries can appear in any order, and a
  single trace can satisfy several entries at once.
- **An absent list, or `[]`, asserts nothing.** The run is judged on `expectedException` alone.
- **An empty or whitespace-only entry makes the run red.** Every message contains the empty
  string, so such an entry is not a wildcard: it is reported as invalid, with its position in the
  list.
- **`expectedException` and `expectedTraceLog` combine with AND.** Both must hold for the run to
  pass, and the traces are evaluated also when the plugin throws the expected exception and that
  exception is captured. When the expected exception never arrives, the run is already red and keeps
  the `expectedException` diagnostic.

A missing trace fails the run like any other failed expectation. The summary reports
`Execution Failed!`, then `Error Type: XrmGhost.ExpectedTraceLogAssertion` — not a CLR type: nothing
was thrown, the name tells a missing trace apart from an exception the plugin raised — and an
`Error Message:` listing the entries no plugin trace contained (and the positions of any blank
entries). The traces and the rest of the output are kept, so you can compare what the plugin
actually traced with what you declared, and `xg run` exits with code `1`.

| What happens | Result |
|---|---|
| No `expectedException`, plugin does not throw | Pass — exit code `0` |
| No `expectedException`, plugin throws | Fail — exit code `1` |
| `expectedException` satisfied by some link of the chain | Pass — exit code `0`, summary line `Expected Exception Matched:` |
| `expectedException` declared, plugin throws a different type or a message that does not contain `messageContains` | Fail — exit code `1` |
| `expectedException` declared, plugin throws nothing | Fail — exit code `1` |
| `expectedException` declared with a missing or empty `typeName` | Fail — exit code `1` |
| `expectedTraceLog` absent or `[]` | No trace assertion — the result follows the rows above |
| Every `expectedTraceLog` entry found in a `Plugin` trace, and the exception expectation (if any) holds | Pass — exit code `0` |
| An `expectedTraceLog` entry found in no `Plugin` trace | Fail — exit code `1`, `Error Type: XrmGhost.ExpectedTraceLogAssertion` |
| An `expectedTraceLog` entry that is empty or whitespace-only | Fail — exit code `1`, `Error Type: XrmGhost.ExpectedTraceLogAssertion` |
| `expectedException` satisfied, an `expectedTraceLog` entry missing | Fail — exit code `1`, `Error Type: XrmGhost.ExpectedTraceLogAssertion` |

### Migrating the legacy placeholder

Scenarios generated by earlier releases of `xg generate-scenario` carry a placeholder entry of the
form `Trace log for {messageName} (expected)` — for example `"Trace log for Create (expected)"`.
It used to be ignored; now it is an assertion that no plugin traces, so the run turns red with
`XrmGhost.ExpectedTraceLogAssertion`. For each saved scenario, pick one of three fixes:

- **remove** the `expectedTraceLog` key;
- **empty** it to `"expectedTraceLog": []`;
- **replace** the placeholder with a substring of a trace the plugin really emits.
