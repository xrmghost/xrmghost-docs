# `xg env add`

## Synopsis

```shell
xg env add [--no-interactive]
```

## Description

`xg env add` opens an interactive wizard that collects all the information needed to register a new Dataverse environment with XrmGhost.

### Prerequisite: choose how the environment signs in

The wizard offers five ways to sign in. Delegated sign-in is available from the next stable XrmGhost release onwards. **Client Secret is one method among them, not the only one.** Only the certificate and client secret methods, and the "my own app registration" variants of browser and device code, need a client application registered in Microsoft Entra ID; the wizard does not create the app registration for you.

| Wizard choice | What you need |
|---|---|
| **Browser sign-in (XrmGhost app)** — the default | Nothing to register. You sign in with your own account in a browser, with multi-factor authentication (MFA) when your tenant requires it; on Windows the sign-in can go through Windows Web Account Manager (WAM). |
| **Browser sign-in (my own app registration, ClientId required)** | The Application (client) ID of your own app registration. |
| **Device code (XrmGhost app)** | Nothing to register. You enter a code on a Microsoft page, from any device. |
| **Device code (my own app registration, ClientId required)** | The Application (client) ID of your own app registration. |
| **Certificate (app registration, ClientId required)** | The Application (client) ID, and either a `.pfx` file path (with its password, if it has one) or a thumbprint from the certificate store. |
| **Azure CLI (uses 'az login')** | An `az login` for the environment's tenant. Nothing is stored by XrmGhost. |
| **Client secret (app registration, ClientId required)** | The Application (client) ID and a client secret created for that app registration. |

The signed-in account, or the application user bound to the app registration, needs access to the target environment — in Dataverse, a security role that covers what your plugins read.

The wizard prompts you for the following details in sequence:

1. **Friendly name** — a short, unique label used to reference this environment in other `xg env` commands (e.g. `activate`, `delete`, `refresh`). Must not be empty; uniqueness is enforced by the service layer.
2. **Environment URL** — the full HTTPS URL of your Dynamics 365 / Dataverse organisation (e.g. `https://myorg.crm.dynamics.com`). Must be a valid absolute HTTP/HTTPS URL.
3. **Authentication method** — one of the choices in the table above. The first one, browser sign-in with the XrmGhost app, is the default.
4. **Client ID** — asked only for the choices that say "ClientId required". It must be a GUID. The other choices use the XrmGhost application, and Azure CLI needs none.
5. **Method-specific material** — a client secret (input masked, must not be empty) for **Client secret**; a certificate path or thumbprint, and the certificate password if any (masked), for **Certificate**. Browser, device code and Azure CLI ask for nothing here and store no secret.
6. **Metadata cache lifecycle** — how long XrmGhost keeps Dataverse metadata cached for this environment. Choose from a preset list or enter a custom duration.

After the wizard completes, the environment configuration is saved. A client secret or a certificate password, when the method has one, is stored separately from the configuration, in the platform credential store (Windows Credential Manager on Windows, or an equivalent secure store on other platforms). Tokens, refresh tokens and the signed-in account are never written to the environment configuration.

### Sign-in and per-environment sessions

The wizard registers the environment; it does not sign you in. The CLI signs in the first time it needs a token, for example on `xg env refresh` or `xg env activate`.

- **One session per environment.** Each environment has its own sign-in cache, so two environments, even in the same tenant, never share a session and you can use different accounts for different environments. To remove one, use [`xg env logout`](/cli/reference/env-logout/).
- **The cache comes first.** A sign-in first tries the cached session. A prompt (browser, WAM or device code) appears only when the cache cannot supply a token, and only in an interactive terminal.
- **The cache is encrypted by the operating system** (DPAPI on Windows, Keychain on macOS, libsecret on Linux). On Linux without libsecret the cache stays **in memory only**: no refresh token is written to disk, so the session ends with the process.

### Without a terminal

A prompt needs a person at a terminal. In CI, in a pipe, or in a process driven by a coding agent without a terminal, the CLI cannot show one. If the cache cannot supply a token, the command fails with a message that names the command to re-run; run it in an interactive terminal, then run the original command again. Do not pass credentials to the host process to get around it. See [Use delegated Dataverse authentication](/how-to/use-delegated-dataverse-authentication/).

> **Not supported.** Workload identity and managed identity are not authentication methods of the CLI.

### Tenant resolution (`TenantId`)

`TenantId` is **not** a wizard prompt. When the environment is registered, the CLI resolves the Microsoft Entra tenant on its own:

1. it sends an **unauthenticated** request to `{EnvironmentUrl}/api/data/v9.2/WhoAmI`;
2. it reads the `authorization_uri` parameter from the `WWW-Authenticate` header of the challenge that Dataverse returns, and extracts the tenant from that URI;
3. when a tenant is found, it is saved as `TenantId` in the environment entry of `d365_environments.json`.

The resolution needs the environment URL to be reachable over HTTP, but it does **not** use your credentials. It is **best-effort**: if the request fails or the header does not yield a tenant, the environment is registered anyway, with an empty `TenantId`, and the command does not fail because of it. An empty `TenantId` is filled in later, when you run [`xg env activate`](/cli/reference/env-activate/) on that environment.

> **License requirement:** `xg env add` requires a **Pro** license tier. Running it without a valid Pro subscription will produce an error before the wizard starts.

### Interactive-only mode

`xg env add` is fully interactive — there is no flag to pre-fill values. All inputs must be entered at the terminal prompt. `--no-interactive` exists only so that a script gets a clear refusal: the command exits with `1` and tells you to run `xg env add` in an interactive terminal. The same refusal applies when there is no terminal (a pipe, CI, an agent without a terminal). To register environments from a script, use [`xg env import`](/cli/reference/env-import/).

### Metadata cache lifecycle presets

The wizard offers the following preset durations. Select **Custom** to enter a value manually.

| Preset | Duration |
|---|---|
| `1 hour` | 1 hour |
| `4 hours` | 4 hours |
| `1 day` | 24 hours |
| `1 week` *(default)* | 7 days |
| `2 weeks` | 14 days |
| `1 month` | ~30 days |
| `Custom` | User-specified (see format below) |

**Custom duration format:** a positive integer followed by a unit suffix — `m` (minutes), `h` (hours), or `d` (days). Examples: `30m`, `12h`, `3d`.

## Options

`xg env add` takes no arguments. The entire configuration is gathered through the interactive wizard.

| Flag | Type | Default | Description |
|---|---|---|---|
| `--no-interactive` | flag | `false` | Refuse to run: adding an environment needs a terminal. |

## Exit Codes

| Code | Meaning |
|---|---|
| `0` | Environment added successfully. |
| `1` | Wizard cancelled, required information was missing, a duplicate friendly name was supplied, or there is no terminal (or `--no-interactive` was given). |
| `-1` | License tier check failed (Pro license required). |

## Examples

### Add a new environment (basic)

```shell
xg env add
```

Launch the wizard and follow the prompts to register a new Dataverse environment. After completing all steps, the environment is available immediately for use with other `xg env` commands.

### Add an environment and verify it was registered

```shell
xg env add
xg env list
```

Run `xg env add` to register the environment, then run `xg env list` to confirm it appears in the list of configured environments.
