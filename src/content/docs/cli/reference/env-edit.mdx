# `xg env edit`

Edit an existing Dynamics 365 environment configuration interactively.

:::info Pro licence required
`env edit` is a **Pro-tier** feature. Ensure your licence is active and at the Pro level before running this command. Use [`xg license status`](/cli/reference/license-status/) to verify.
:::

## Synopsis

```
xg env edit <FRIENDLY_NAME> [--no-interactive]
```

## Description

`xg env edit` opens an interactive wizard that lets you modify the settings of a previously registered Dataverse environment. The environment is identified by its **friendly name** — a short human-readable label you assigned when the environment was first added.

Once invoked, the wizard pre-populates every prompt with the current value of the field. Press **Enter** to accept the existing value, or type a replacement to overwrite it.

### What the wizard edits

The wizard walks you through the following fields in order:

1. **Friendly name** — the human-readable label used to identify the environment in all other commands.
2. **Environment URL** — the Dataverse organisation URL (e.g., `https://myorg.crm.dynamics.com`). Must be a valid absolute `https://` URL.
3. **Authentication method** — browser sign-in with MFA (or WAM on Windows), device code, certificate, Azure CLI or client secret, each in the XrmGhost-app or own-app-registration form where one exists. The method the environment uses now is listed first, so confirming it changes nothing. The choices are the same as in [`xg env add`](/cli/reference/env-add/#prerequisite-choose-how-the-environment-signs-in). An environment saved before delegated sign-in existed is shown as **Client secret**.
4. **Client ID** — asked only for the choices that say "ClientId required"; it must be a GUID. The other choices use the XrmGhost application, and Azure CLI keeps the value already stored.
5. **Method-specific material** — for **Client secret**, the secret (leave blank to keep the existing one, when the environment already used a client secret); for **Certificate**, a `.pfx` path or a thumbprint, and the certificate password (leave blank to keep the existing one, or if there is none). The other methods ask for nothing and store no secret.
6. **Metadata cache lifecycle** — how long the Dataverse metadata cache is considered fresh before an automatic refresh is triggered. Select from a preset list or enter a custom duration.

:::note Changing the Environment URL invalidates the stored TenantId
The `TenantId` stored for the environment is derived from its Environment URL, so `env edit` invalidates it (saves it as empty) only when the URL really changes. Differences of only a trailing slash or of letter case do not count as a change and keep the stored `TenantId`. `env edit` does not probe the new URL: the next run of [`xg env activate <FRIENDLY_NAME>`](https://docs.xrmghost.tech/cli/reference/env-activate/) makes a best-effort attempt to recalculate it, even if the edited environment is already the active one.
:::

### Secret handling

The client secret and the certificate password are stored separately from the environment configuration file, and only for the method that uses them. When editing:

- If you enter a new secret, it replaces the stored secret.
- If you leave the secret prompt blank, the existing stored secret is preserved.
- If you also change the friendly name, the secret is automatically migrated to use the new name as its identifier. The old secret entry is removed.

Tokens, refresh tokens and the signed-in account are never part of the configuration. Each environment has its own sign-in session; to discard it, use [`xg env logout`](/cli/reference/env-logout/).

### Metadata cache lifecycle presets

The wizard offers the following preset durations for the metadata cache lifecycle:

| Option | Duration |
|---|---|
| `1 hour` | 1 hour |
| `4 hours` | 4 hours |
| `1 day` | 24 hours |
| `1 week` | 7 days _(default)_ |
| `2 weeks` | 14 days |
| `1 month` | 30 days (approximate) |
| `Custom` | User-defined — enter a value such as `30m`, `2h`, or `3d` |

Custom durations use the suffix `m` (minutes), `h` (hours), or `d` (days).

## Arguments

| Argument | Required | Description |
|---|---|---|
| `<FRIENDLY_NAME>` | Yes | The friendly name of the environment configuration to edit. Must match an existing registered environment exactly. |

## Options

All editable fields are collected interactively by the wizard after invocation.

| Option | Description |
|---|---|
| `--no-interactive` | Refuse to run: editing an environment needs a terminal. The command exits with `1` and names the command to re-run in an interactive terminal. |
| `--help` | Display help information for this command and exit. |

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Environment updated successfully. |
| `1` | Error — environment not found, wizard cancelled, no terminal (or `--no-interactive` given), or an unexpected failure occurred. |

## Examples

### Edit an environment interactively

```shell
xg env edit "My Dev Org"
```

Launches the interactive wizard for the environment registered as `My Dev Org`. Each prompt is pre-populated with the current value; press Enter to keep it or type a new value to replace it.

### Rename an environment and update the Client Secret

```shell
xg env edit staging-old
```

Run the wizard, change the friendly name from `staging-old` to `staging-v2`, enter a new Client Secret when prompted, and confirm all other fields. The secret is automatically migrated to the new name.

### Change only the metadata cache lifecycle

```shell
xg env edit "Production"
```

Accept every prompt with its current value (press Enter) until you reach the metadata cache lifecycle selection. Choose `Custom`, then enter `1d` to set the cache to expire after 1 day.

## Non-interactive usage

`env edit` always launches an interactive wizard — it cannot be driven entirely from CLI flags in the current version. To automate environment management, consider exporting the configuration with [`env export`](/cli/reference/env-export/), editing the JSON file, and re-importing it with [`env import`](/cli/reference/env-import/).

Without a terminal (a CI pipeline, a pipe, a coding agent without a terminal) or with `--no-interactive`, the command is refused before any prompt and exits with code `1`, naming the command to re-run in an interactive terminal. Use scripted `env import` workflows for non-interactive environments.
