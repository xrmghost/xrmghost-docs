# Getting Started

XrmGhost runs your Dynamics plugins and tests on your machine. This page takes you from nothing installed to a first local run.

It's three steps: install the CLI, confirm the runtime host, run.

## Prerequisites

The primary channel is a **signed, self-contained ZIP for Windows x64**. What you need depends on how you install:

| Channel | Requirement | Why |
| --- | --- | --- |
| **Signed ZIP (win-x64)** — primary | **.NET Framework 4.7.2** | Runs the host that executes your plugins, matching the Dataverse server-side runtime. `xg.exe` is self-contained: no .NET runtime is needed for the CLI itself. |
| **.NET global tool** — soft-deprecated | **.NET 9 runtime** and **.NET Framework 4.7.2** | The global tool runs `xg` on the shared .NET 9 runtime; the host still needs 4.7.2. |

On Windows 10/11 the 4.7.2 framework is almost always already there; on a clean build agent it may not be. If you stay on the global tool, check for the .NET 9 runtime with `dotnet --list-runtimes` and look for a `Microsoft.NETCore.App 9.x` line.

## 1. Install the CLI

### Download the signed ZIP

Stable releases are published on the public repository's release page: **[github.com/xrmghost/xrmghost/releases](https://github.com/xrmghost/xrmghost/releases)**. Download the asset named `xrmghost-cli-<version>-full.zip` — the full bundle that carries both `xg.exe` and the host. The archive without the `-full` suffix contains the executable alone and is not the one to install.

> **TODO:** The first signed stable ZIP of the CLI is not published yet. The direct download link for the stable asset will be added here once it is on the release page, as part of ADO-2619.

Before extracting, check who signed it: the publisher to expect and how to verify it (including WDAC policies) are described in **[Trust and WDAC](/cli/trust-and-wdac/)**.

### Extract it and add the folder to PATH

Extract the ZIP to a folder of its own, for example `C:\Tools\XrmGhost`. The layout is:

```text
C:\Tools\XrmGhost\
├── xg.exe      the CLI
└── bin\        the signed host that executes your plugins
```

Add **the folder that contains `xg.exe`** — `C:\Tools\XrmGhost`, not `bin\` — to your user `PATH` (*Settings → System → About → Advanced system settings → Environment Variables*). Then open a new shell, so the new `PATH` is picked up, and confirm:

```powershell
xg --version
```

To update later, download the newer `-full.zip` and extract it over the same folder: `xg.exe` and `bin\` move together.

### Migrating from the global tool

If you previously installed XrmGhost with `dotnet tool install -g XrmGhost.Cli`, that installation left an `xg` shim in `%USERPROFILE%\.dotnet\tools`, which is on your `PATH` too. Two `xg` commands on the `PATH` means the one that runs depends on the order of the entries. Find every `xg` your shell can see:

```powershell
Get-Command xg -All | Select-Object Source
```

(from `cmd`, `where xg` gives the same list). If a line points to `.dotnet\tools`, remove the old shim:

```powershell
dotnet tool uninstall -g XrmGhost.Cli
```

If you need to keep the global tool installed for now, make sure the ZIP folder comes **before** `%USERPROFILE%\.dotnet\tools` in your `PATH`. Either way, open a new shell and run `Get-Command xg -All` again: the first line must be the `xg.exe` in the folder you extracted.

### Other channels

- **.NET global tool — soft-deprecated.** The `XrmGhost.Cli` package stays on NuGet and is not unlisted, but it is no longer the recommended channel: a global tool cannot be shipped as a signed executable. It needs the .NET 9 runtime, and it does not carry the host.
- **winget — not published yet.** `winget install XrmGhost.Cli` becomes an option only after the first signed stable ZIP is released and the submission has passed the external review of `winget-pkgs`. Until then, use the ZIP. The publication contract is described in **[winget publication](/cli/winget-publication/)**.
- **Alpha builds are not signed.** Prereleases are not code-signed, so Windows Smart App Control may block them. Use them only if you need a fix before it reaches a stable release.

## 2. Confirm the runtime host

The CLI is light. The component that actually executes your plugins is the **host** — a .NET Framework 4.7.2 process that mirrors the Dataverse server-side runtime. With the ZIP, the signed host is already in the `bin\` folder next to `xg.exe`: there is nothing separate to download, and `xg` uses that host before any other installation it finds.

Check that the CLI sees it:

```powershell
xg doctor
```

`xg doctor --verbose` also prints the resolved host path, which should point inside the `bin\` folder of your extracted ZIP.

## 3. Run

With CLI and host in place, you're ready. From a project that contains your plugins:

```powershell
xg --help
```

From here the command set covers running plugins locally, building and replaying test scenarios, and inspecting what happened. The [CLI Reference](/cli/) is the full map.
