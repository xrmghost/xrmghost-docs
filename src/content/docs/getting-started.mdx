# Getting Started

XrmGhost runs your Dynamics plugins and tests on your machine. This page takes you from nothing installed to a first local run.

It's three steps: download the signed ZIP, run `xg init`, run `xg run`.

## Prerequisites

XrmGhost runs on **Windows x64** and needs **.NET Framework 4.7.2** or later. The CLI itself is self-contained — no .NET runtime is needed for `xg.exe` — but the host that executes your plugins is a .NET Framework 4.7.2 process, matching the Dataverse server-side runtime. On Windows 10/11 the 4.7.2 framework is almost always already there; on a clean build agent it may not be. `xg init` checks it for you.

## 1. Install the CLI

XrmGhost is distributed as a signed ZIP on GitHub Releases, the public repository's release page: **[github.com/xrmghost/xrmghost/releases](https://github.com/xrmghost/xrmghost/releases/latest)**. Pick the asset named `xrmghost-cli-<version>-full.zip`: it carries both `xg.exe` and the signed host that executes your plugins, so there is nothing separate to download. Before extracting, check who signed it, as described in **[Trust and WDAC](/cli/trust-and-wdac/)**.

Extract the ZIP to a folder of its own, for example `C:\Tools\XrmGhost`. The layout is:

```text
C:\Tools\XrmGhost\
├── xg.exe      the CLI
└── bin\        the signed host that executes your plugins
```

Add **the folder that contains `xg.exe`** — `C:\Tools\XrmGhost`, not `bin\` — to your user `PATH` (*Settings → System → About → Advanced system settings → Environment Variables*), open a new shell and confirm:

```powershell
xg --version
```

**Alpha builds are not signed.** Prereleases are not code-signed, so Windows Smart App Control may block them. Use them only if you need a fix before it reaches a stable release.

### Updating

To update, download the newer `xrmghost-cli-<version>-full.zip` and extract it over the same folder: `xg.exe` and `bin\` move together. The host in `bin\` is updated **only** this way — neither `xg doctor --fix` nor `xg setup host` changes it, because both work on a separate, managed install that the bundled host takes precedence over.

### Moving a desktop off the global tool

If you previously installed XrmGhost with `dotnet tool install -g XrmGhost.Cli`, that installation left an `xg` shim in `%USERPROFILE%\.dotnet\tools`, which is on your `PATH` too. Two `xg` commands on the `PATH` means the one that runs depends on the order of the entries — and you may end up running a CLI older than the ZIP you extracted. `xg init` warns when it finds the shim. Find every `xg` your shell can see:

```powershell
Get-Command xg -All | Select-Object Source
```

(from `cmd`, `where xg` gives the same list). If a line points to `.dotnet\tools`, remove the old shim:

```powershell
dotnet tool uninstall --global XrmGhost.Cli
```

Then open a new shell and run `Get-Command xg -All` again: the first line must be the signed `xg.exe` from the ZIP folder.

## 2. Run `xg init`

The CLI is light. The component that actually executes your plugins is the **host** — a .NET Framework 4.7.2 process that mirrors the Dataverse server-side runtime. `xg init` prepares the machine to run it:

```powershell
xg init
```

It reports which `xg` is running and from which channel, checks Windows and .NET Framework 4.7.2, and resolves the host. With the ZIP, the host is the one in the `bin\` folder next to `xg.exe`, which takes precedence over any other installation; `init` uses it as is. If no usable host is found, `init` installs the latest one into the managed install root (`%LOCALAPPDATA%\xrmghost\framework-host\`). It ends with the one next step that applies to you — activate a license with `xg license activate`, register an environment with `xg env add`, or start running plugins.

`init` exits `0` when the host is healthy or has been repaired, and `1` when the setup is in a state it cannot repair — the message says what to do. The details are in the [`xg init` reference](/cli/reference/init/).

## 3. Run

With CLI and host in place, you're ready. From a project that contains your plugins:

```powershell
xg run -a .\bin\Debug\MyPlugins.dll -t MyPlugins.AccountPreCreate
```

The full set of options is in the [`xg run` reference](/cli/reference/run/); the [CLI Reference](/cli/) is the full map of commands.

### In CI

On a build agent the flow is the same ZIP, with prompts turned off. Run `xg init --no-interactive` before `xg run --no-interactive`:

```powershell
xg init --no-interactive
xg run --no-interactive -a .\bin\Release\MyPlugins.dll -t MyPlugins.AccountPreCreate -s .\scenarios\account-create.json
```

Neither command prompts or opens an interactive sign-in. `xg run --no-interactive` never downloads the host: if no usable host is found, it stops with a non-zero exit code and points to `xg init --no-interactive`. `xg init --no-interactive` still installs the host into the managed root when the setup requires it — that is what it is for. The agent must be Windows, because the host is a .NET Framework 4.7.2 process.
