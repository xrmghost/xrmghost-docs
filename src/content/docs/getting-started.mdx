# Getting Started

XrmGhost runs your Dynamics plugins and tests on your machine. This page takes you from nothing installed to a first local run.

It's three steps: install the CLI, run `xg init`, run `xg run`.

## Prerequisites

XrmGhost runs on **Windows x64**. The three desktop methods install the same signed ZIP, including `xg.exe` and the host that executes your plugins. The ZIP is signed by Agostini Lab Srl; [Trust and WDAC](/cli/trust-and-wdac/) explains how to verify it.

## 1. Install the CLI

<InstallMethods />

### In CI only: the .NET global tool

On build agents and in automation, install the `XrmGhost.Cli` package from NuGet as a .NET global tool:

```powershell
dotnet tool install --global XrmGhost.Cli
```

This channel is for **CI and automation only** — on a desktop, use one of the methods above. The package does not carry the host, so the pipeline installs it with `xg init --no-interactive` before running anything:

```powershell
dotnet tool install --global XrmGhost.Cli
xg init --no-interactive
xg run --no-interactive -a .\bin\Release\MyPlugins.dll -t MyPlugins.AccountPreCreate -s .\scenarios\account-create.json
```

None of these commands prompts or opens an interactive sign-in. `xg init --no-interactive` installs the host from the public release page into `%LOCALAPPDATA%\xrmghost\framework-host\` when the agent has none. The agent must be Windows, because the host is a .NET Framework 4.7.2 process. To update the CLI on an agent that keeps its tools between runs, run `dotnet tool update --global XrmGhost.Cli`.

### Moving a desktop off the global tool

If you previously installed XrmGhost on your desktop with `dotnet tool install -g XrmGhost.Cli`, that installation left an `xg` shim in `%USERPROFILE%\.dotnet\tools`, which is on your `PATH` too. Two `xg` commands on the `PATH` means the one that runs depends on the order of the entries. Find every `xg` your shell can see:

```powershell
Get-Command xg -All | Select-Object Source
```

If a line points to `.dotnet\tools`, remove the old shim:

```powershell
dotnet tool uninstall -g XrmGhost.Cli
```

If you need to keep the global tool installed for now, make sure the Scoop, PowerShell, or ZIP folder comes **before** `%USERPROFILE%\.dotnet\tools` in your `PATH`. Open a new shell and run `Get-Command xg -All` again: the first line must be the signed `xg.exe`.

**Alpha builds are not signed.** Prereleases may be blocked by Smart App Control.

## 2. Run `xg init`

The CLI is light. The component that actually executes your plugins is the **host** — a .NET Framework 4.7.2 process that mirrors the Dataverse server-side runtime.

```powershell
xg init
```

It reports which `xg` is running and from which channel, checks Windows and .NET Framework 4.7.2, and resolves the host. With Scoop, PowerShell, or the ZIP, the signed host is already in the `bin\` folder next to `xg.exe`. If no usable host is found — as with the global tool in CI — `init` installs the latest one into the managed install root (`%LOCALAPPDATA%\xrmghost\framework-host\`).

## 3. Run

With CLI and host in place, you're ready:

```powershell
xg run -a .\bin\Debug\MyPlugins.dll -t MyPlugins.AccountPreCreate
```

The full set of options is in the [`xg run` reference](/cli/reference/run/); the [CLI Reference](/cli/) is the full map of commands. In CI, use `xg init --no-interactive` and `xg run --no-interactive` as shown above.
