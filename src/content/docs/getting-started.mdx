# Getting Started

XrmGhost runs your Dynamics plugins and tests on your machine. This page takes you from nothing installed to a first local run.

It's three steps: install the CLI, confirm the runtime host, run.

## Prerequisites

XrmGhost runs on **Windows x64**. What you need depends on how you install:

| Channel | Use it for | Requirement | Why |
| --- | --- | --- | --- |
| **winget** — recommended | Your development machine | **.NET Framework 4.7.2** | Installs the signed, self-contained `xg.exe` together with the host that executes your plugins, matching the Dataverse server-side runtime. No .NET runtime is needed for the CLI itself. |
| **.NET global tool** — CI only | Build agents and automation | **.NET 9 runtime** and **.NET Framework 4.7.2** | The global tool runs `xg` on the shared .NET 9 runtime; the host still needs 4.7.2. |
| **Signed ZIP** | Machines without winget | **.NET Framework 4.7.2** | The same signed bundle winget installs, downloaded by hand. |

On Windows 10/11 the 4.7.2 framework is almost always already there; on a clean build agent it may not be. For the global tool, check for the .NET 9 runtime with `dotnet --list-runtimes` and look for a `Microsoft.NETCore.App 9.x` line.

## 1. Install the CLI

### Install with winget

On your development machine, install with the Windows Package Manager:

```powershell
winget install XrmGhost.Cli
```

This installs the signed `xg.exe` and, in the `bin\` folder next to it, the signed host that executes your plugins: there is nothing separate to download. winget adds the install folder to your `PATH`; open a new shell, so the new `PATH` is picked up, and confirm:

```powershell
xg --version
```

To update later:

```powershell
winget upgrade XrmGhost.Cli
```

The publisher to expect and how to verify the signature (including WDAC policies) are described in **[Trust and WDAC](/cli/trust-and-wdac/)**.

### In CI only: the .NET global tool

On build agents and in automation, install the `XrmGhost.Cli` package from NuGet as a .NET global tool:

```powershell
dotnet tool install --global XrmGhost.Cli
```

This channel is for **CI and automation only** — on a desktop, use winget. The package does not carry the host: on the first `xg run` or `xg generate-scenario` the CLI downloads it from the public release page into `%LOCALAPPDATA%\xrmghost\framework-host\`. To keep that step out of the run itself, install the host explicitly in the pipeline with [`xg setup host`](/cli/reference/setup-host/); with `--no-interactive`, a run fails instead of downloading a missing host. The agent must be Windows, because the host is a .NET Framework 4.7.2 process.

### Last option: download the signed ZIP

If winget is not available, download the same bundle by hand from the public repository's release page: **[github.com/xrmghost/xrmghost/releases](https://github.com/xrmghost/xrmghost/releases/latest)**. Pick the asset named `xrmghost-cli-<version>-full.zip`: it carries both `xg.exe` and the host. Before extracting, check who signed it, as described in **[Trust and WDAC](/cli/trust-and-wdac/)**.

Extract the ZIP to a folder of its own, for example `C:\Tools\XrmGhost`. The layout is:

```text
C:\Tools\XrmGhost\
├── xg.exe      the CLI
└── bin\        the signed host that executes your plugins
```

Add **the folder that contains `xg.exe`** — `C:\Tools\XrmGhost`, not `bin\` — to your user `PATH` (*Settings → System → About → Advanced system settings → Environment Variables*), open a new shell and run `xg --version`. To update later, download the newer `-full.zip` and extract it over the same folder: `xg.exe` and `bin\` move together.

### Moving a desktop off the global tool

If you previously installed XrmGhost on your desktop with `dotnet tool install -g XrmGhost.Cli`, that installation left an `xg` shim in `%USERPROFILE%\.dotnet\tools`, which is on your `PATH` too. Two `xg` commands on the `PATH` means the one that runs depends on the order of the entries. Find every `xg` your shell can see:

```powershell
Get-Command xg -All | Select-Object Source
```

(from `cmd`, `where xg` gives the same list). If a line points to `.dotnet\tools`, remove the old shim:

```powershell
dotnet tool uninstall -g XrmGhost.Cli
```

If you need to keep the global tool installed for now, make sure the winget or ZIP folder comes **before** `%USERPROFILE%\.dotnet\tools` in your `PATH`. Either way, open a new shell and run `Get-Command xg -All` again: the first line must be the signed `xg.exe`.

**Alpha builds are not signed.** Prereleases are not code-signed, so Windows Smart App Control may block them. Use them only if you need a fix before it reaches a stable release.

## 2. Confirm the runtime host

The CLI is light. The component that actually executes your plugins is the **host** — a .NET Framework 4.7.2 process that mirrors the Dataverse server-side runtime. With winget or the ZIP, the signed host is already in the `bin\` folder next to `xg.exe`, and `xg` uses that host before any other installation it finds.

Check that the CLI sees it:

```powershell
xg doctor
```

`xg doctor --verbose` also prints the resolved host path, which should point inside the `bin\` folder next to `xg.exe`. With the global tool in CI, it points to the host downloaded under `%LOCALAPPDATA%\xrmghost\framework-host\`.

## 3. Run

With CLI and host in place, you're ready. From a project that contains your plugins:

```powershell
xg --help
```

From here the command set covers running plugins locally, building and replaying test scenarios, and inspecting what happened. The [CLI Reference](/cli/) is the full map.
