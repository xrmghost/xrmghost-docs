# From zero to a locally tested Dataverse plugin in 10 minutes

The slow part of a Dataverse plugin is not writing it. It is finding out whether it works: build, deploy, trigger the message, wait, open the trace log. This page runs the compiled plugin on your machine instead, against one scenario, and shows what a failure looks like when it happens locally.

Ten minutes assumes a Windows machine with a plugin project that builds. Everything you type is below; everything you should see is marked.

## Prerequisites

- **Windows 10/11, x64.** The host that executes your plugin is a .NET Framework 4.7.2 process; on Windows that framework is almost always already installed.
- **A plugin project that builds**, targeting .NET Framework (plugin assemblies for Dataverse target `net462`), with `Microsoft.CrmSdk.CoreAssemblies` referenced.
- **A terminal.** PowerShell is used here; `cmd` works the same.

## 1. Install the CLI and check it

On a desktop, install with winget:

```powershell
winget install XrmGhost.Cli
```

This puts `xg.exe` and the host on your machine and on your `PATH`. If you prefer not to use winget, the signed ZIP on the [release page](https://github.com/xrmghost/xrmghost/releases) (asset `xrmghost-cli-<version>-full.zip`, which carries `xg.exe` and the host in `bin\`) is the same build; the [Getting Started](/getting-started/) page covers unpacking it and adding it to `PATH`. In CI or automation, `dotnet tool install -g XrmGhost.Cli` from NuGet is the right channel.

## 2. Describe the plugin with attributes

XrmGhost builds a scenario from metadata it reads on the plugin class, through the [`XrmGhost.Attributes`](/attributes/) package. Add it to the plugin project:

```powershell
dotnet add package XrmGhost.Attributes
```

The plugin for this page runs on `Create` of an account, pre-operation, and writes a description that names the primary contact:

```csharp
using System;
using Microsoft.Xrm.Sdk;
using XrmGhost.Attributes;

namespace Contoso.Plugins
{
    [PluginExecutionConfig("account", "Create", Stage = 20, Mode = 0)]
    [HandlesMessage("Create")]
    public class AccountCreatePlugin : IPlugin
    {
        public void Execute(IServiceProvider serviceProvider)
        {
            var context = (IPluginExecutionContext)serviceProvider.GetService(typeof(IPluginExecutionContext));
            var tracing = (ITracingService)serviceProvider.GetService(typeof(ITracingService));

            var target = (Entity)context.InputParameters["Target"];
            var contact = target.GetAttributeValue<EntityReference>("primarycontactid");

            tracing.Trace("Account '{0}', primary contact '{1}'", target.GetAttributeValue<string>("name"), contact.Name);
            target["description"] = $"Primary contact: {contact.Name}";
        }
    }
}
```

What each attribute feeds into the scenario:

- `PluginExecutionConfig` supplies the primary entity, the stage and the mode of the generated execution context.
- `HandlesMessage` decides which messages get a scenario file: one file per declared message. Without it, the generator defaults to `Create`.
- `InputParameter`, `PreImage`, `PostImage` and `SharedVariable` (not used here) seed input parameters, images and shared variables with the JSON you give them, so a scenario can start closer to the real record.

The attributes do nothing at run time in Dataverse. They are metadata, read by reflection, and the [attribute reference](/attributes/reference/) lists each one.

Build the project:

```powershell
dotnet build -c Release
```

The CLI starts the host for a moment, asks it for the plugin's metadata, writes the file and stops the host. Pass `-o` a plain file name, as above: it lands in the current directory. The generated `account-create.json` has an `executionContext` with `messageName`, `primaryEntityName`, `stage` and `mode` taken from the attributes, a `Target` with a sample `name` and a default `ownerid`, and a mocked `usersettings` record for the calling user. The [Scenario Files](/cli/scenarios/) page is the reference for everything in it.

The plugin reads `primarycontactid`, which the scaffold does not know about. Add it to `inputParameters.Target.attributes`, next to `name`:

```json
"primarycontactid": {
  "logicalName": "contact",
  "id": "00000000-0000-0000-0000-0000000000c1",
  "name": "Alex Taylor"
}
```

The exception type, the message and the stack trace pointing at `Execute` arrive in the same terminal, seconds after the run, not in a trace log after a deployment. `xg run` exits `1`.

The fix is the usual one:

```csharp
var contact = target.GetAttributeValue<EntityReference>("primarycontactid");
if (contact == null)
{
    tracing.Trace("Account '{0}' has no primary contact; description left unchanged.", target.GetAttributeValue<string>("name"));
    return;
}
```

Rebuild and rerun. The host reads the assembly bytes and does not lock the file, so a rebuild while you iterate is picked up by the next run.

Keep both scenarios. `account-create.json` with the contact and a copy without it are two cases you can rerun after every change: one scenario per run, so a regression check is a loop of `xg run` invocations, not one command.

The [`xg run`](/cli/reference/run/) reference covers that and the other flags.

## What this loop does not cover

- The data the plugin reads is what the scenario says. On Standard, `Retrieve` and `RetrieveMultiple` are served from the scenario's mocks; on Pro, read-only queries can resolve against a live environment. See [Editions](/editions/).
- The host mirrors the Dataverse server-side plugin model; it is not Dataverse. A green local run is a reason to deploy, not a reason to skip validating in your target environment.
- One scenario per run.
